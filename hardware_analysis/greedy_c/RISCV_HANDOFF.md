# Token selection on RISC-V: handoff

This is the one stage of the detector we are moving to the RISC-V core. Everything you need to
implement it, test it and measure it is listed here.

## 1. Why this stage

The detector runs a small CNN that scores every 16×16-pixel cell of the image, then keeps only the
K most important cells as transformer tokens. Choosing those K cells ("token selection") is a
greedy loop where every step depends on the previous one. On the GPU it took **46 % of the whole
pipeline** (8.9 ms of 19.3 ms) because each step is a tiny kernel launch. On a CPU with the
algorithm below it takes about 0.7 ms. The rest of the network stays on the accelerator.

## 2. What the function must compute (final spec)

Input: a score map `score[i]`, `i = D*r + c`, `D × D` cells, each score a **10-bit unsigned
integer (0 … 1023)**. Output: up to K cell indices `picks[0 … n-1]`, in the order they were picked.

```
repeat until K cells are picked or no free cell is left:
    take the free cell with the highest score
        (ties: the lower index i wins, i.e. raster order, top-left first)
    append it to picks
    mark it and its 3×3 neighbourhood as not free (clip at the borders)
return n = number of picks (n <= K)
```

| Parameter | Values to support |
|---|---|
| Grid D | **32** (512 px input, the paper setting) and 64 (1024 px input) |
| K | **128** and 256 |
| Score bits | **10** (values 0 … 1023) |

On a 32×32 grid the greedy runs out of free cells at about 200–210 picks, so **K = 256 returns
n < 256** there (202–210 on the test images). That is expected, not a bug: return n.

## 3. How 10 bits are stored in C

C has no 10-bit type. The test data stores each score in a **`uint16_t`**; the value is 0 … 1023 and
the upper 6 bits are always zero. That is the simple baseline and what the reference code uses.

If memory matters, two denser layouts are possible (not implemented):
- **3 scores per 32-bit word** (bits 0–9, 10–19, 20–29; 2 bits unused): a 32×32 map takes
  342 words = 1,368 B instead of 2,048 B. Reading a score is one load, a shift and a mask.
- **Fully packed** (4 scores in 5 bytes): 1,280 B, but scores straddle word boundaries.

The unpack cost (shift + mask per score read) is a natural target for a custom instruction or a
dedicated buffer, if you go that way.

## 5. Reference algorithm: bucket-scan (`greedy_c/greedy_bucketscan.c`)

Exact, and the cheapest variant we measured. Two phases:

1. **Link pass.** For `i` from the last cell down to 0: `next[i] = head[score[i]]; head[score[i]] = i`.
   This puts every cell in a linked list ("bucket") per score value. Walking backwards and inserting
   at the front leaves every list in increasing index order, which gives the tie rule for free.
2. **Walk.** For `v` from 1023 down to 0, follow bucket `v`. For each cell: if its bit in the
   blocked bitmap is set, skip it. Otherwise record the pick and set the bits of its 3×3
   neighbourhood. Stop after K picks.

**For 10-bit, the existing file needs exactly two changes:**
```c
#define NUM_SCORES 1024                                // was 256
static const unsigned short FIX_MAP[FIX_CELLS] = ...;  // was unsigned char (in fixation_matrix.h)
```
This was verified natively (gcc -O2): **12/12** golden files match (3 images × 2 grids × K = 128, 256).
`head[]` and `next_cell[]` can stay `short`, since cell indices go up to 4,095.

**Memory, 10-bit:**

| Array | 32×32 | 64×64 | Note |
|---|---:|---:|---|
| score map (`uint16_t`) | 2,048 B | 8,192 B | read-only input |
| `head[1024]` (`int16`) | 2,048 B | 2,048 B | one entry per score value |
| `next_cell[D*D]` (`int16`) | 2,048 B | 8,192 B | |
| blocked bitmap (32-bit words) | 128 B | 512 B | 1 / 2 words per row |
| `picks[K]` | ≤ 1,024 B | ≤ 1,024 B | `int`; `uint16_t` would halve it |

**Cost model (array loads + stores, K = 128, mean over 300 COCO images):**

| Score bits | Buckets | 32×32 | 64×64 |
|---:|---:|---:|---:|
| 8 | 256 | 6,192 | 18,130 |
| **10** | **1,024** | **7,523** | **19,337** |
| 12 | 4,096 | 12,850 | 24,166 |
| naive loop (any) | — | 262,144 | 1,048,576 |

The link pass costs 4 accesses per cell (load score, load head, store next, store head), so it
dominates on 64×64. The walk also touches every bucket head, including empty ones, so more score
levels cost more on the small grid.

**Where the instructions go** (observations, not prescriptions):
- **Link pass:** a fixed load / load / store / store pattern per cell.
- **Blocked test + 3×3 claim:** a shift/AND per test; three read-modify-writes (OR of a 3-bit
  mask into rows r−1, r, r+1) per pick.
- **Walking empty buckets:** one `head[v]` load per score level, even when the bucket is empty.
- **Fixed-size, frequently accessed tables:** `head[]` (2 KB) and the bitmap are candidates for
  dedicated storage.

## 6. Testing

- `greedy_c/test_greedy_c.py` builds each C file natively and for rv32im (`riscv64-unknown-elf-gcc
  -march=rv32im -mabi=ilp32`, run under `qemu-riscv32`) and compares with the golden picks. It
  currently reads the **8-bit** folder; point `TESTDATA` at a 10-bit folder and write `FIX_MAP` as
  `unsigned short` in `write_header()` to test 10-bit.
- The rv32 build computes a checksum `cs = n; cs = cs * 31 + pick` (32-bit wrap) over the picks,
  so a bare-metal run only has to return one number.

**Known issues in the rv32 harness:**
1. At -O2, GCC turns the hand-written `memset` in the startup code into a call to `memset` itself,
   which recurses until the stack overflows and the run segfaults. Fix: add
   `-fno-tree-loop-distribute-patterns` (or `-ffreestanding`) to the rv32 compile line. With that,
   `greedy_naive.c` passes 9/9.
2. `greedy_sortscan.c` and `greedy_bucketscan.c` still segfault under `qemu-riscv32`, even with
   fix 1. **Not diagnosed yet.** Their ELF has a BSS-only read-write segment of about 13.8 KB
   (`order`/`next_cell`, `start`/`head`, `blocked`). Check how qemu-user and the minimal `_start`
   handle it first. Native builds of the same files are correct.
